## What was wrong, and what changed afterwards

This is the part that matters. The generated code did not work first time, and several defects
were only found by running it. Each of these was diagnosed from a real failure and then fixed:

1. **Alembic emitted `CREATE TYPE` twice.** The first migration created the enum types explicitly
   and then `create_table()` created them again, so `alembic upgrade head` died with
   `DuplicateObject: type "category" already exists`. Fixed by declaring the columns with
   `postgresql.ENUM(..., create_type=False)`. See `backend/alembic/versions/0001_initial_schema.py`.

2. **`alembic/env.py` ignored a caller-supplied database URL.** It unconditionally overwrote
   `sqlalchemy.url` from the environment, so the test suite's throwaway database was ignored and
   migrations ran against the host named `database`, which does not resolve locally.

3. **`"not urgent"` was classified as high priority.** The keyword reader matched the substring
   `urgent` inside `not urgent`, so a politely-worded low-priority request scored HIGH. Fixed by
   collapsing negated forms to a marker before the high-signal scan
   (`backend/app/providers/triage/rules.py`).

4. **Fabricated image digests and a fabricated `apt` version pin.** The AI invented plausible-looking
   `sha256:` digests and a `curl=7.88.1-10+deb12u12` pin, neither of which existed. The build failed.
   Real digests were fetched with `docker buildx imagetools inspect`, and the curl dependency was
   removed entirely in favour of the Python interpreter already in the image. **This is the failure
   mode to be most careful of with generated infrastructure code: it produces confident, correctly
   shaped identifiers that do not exist.**

5. **The frontend image crash-looped when the backend was absent.** nginx resolves a literal
   `proxy_pass` hostname once at startup and refuses to boot if it does not resolve, so a frontend
   pod scheduled before the backend had endpoints would never start. Fixed by proxying through a
   variable with a runtime-derived resolver.

6. **nginx overwrote the caller's `X-Request-ID`.** Request tracing broke exactly at the proxy.
   Fixed with a `map` that preserves an incoming id and mints one only when absent.

7. **The submission linter had two false positives of its own** — it flagged healthcheck loopback
   URLs as service-to-service `localhost` use, and misparsed `uvicorn[standard]` when checking that
   the lock file matched `pyproject.toml`. Both were fixed, because a linter that cries wolf gets
   ignored.

  session: the numbers come from commands actually run against this repository, and the failure in

  provider to use.

## Honest statement about the viva

§5.5 says the viva does not care who wrote a line, only whether it can be defended. I am aware that
a line I cannot defend is worth nothing regardless of its author. The commentary throughout this
codebase exists for that reason: every non-obvious decision carries the reasoning inline, so the
code is readable as an argument rather than as an artefact.
