## 1. Three things that differ between my laptop and a CI runner, and the exact line that freezes each

My laptop is an **Apple M1 Pro (arm64), macOS 15.6, 8 cores, 16 GB**, with Docker Desktop given
8 GB. A GitHub runner is **x86-64, Ubuntu 24.04, 4 cores, 16 GB**, fresh every time.

| # | What differs | The line that freezes it |
|---|---|---|
| 1 | **CPU architecture and OS.** My Python is 3.12.12 from pyenv on arm64; the runner's is whatever `setup-python` installs on amd64. Anything compiled locally is the wrong architecture for the runner. | [`backend/Dockerfile:11`](../backend/Dockerfile#L11) — `FROM python:3.12-slim@sha256:f77ac9e4…`. The digest pins the *exact image*, so the interpreter, libc and OS are identical in both places. A tag would not: `python:3.12-slim` moves on every patch release, so a build today and a build next week differ. |
| 2 | **Transitive dependency versions.** `pip install .` resolves at install time. My lockless install in March and the runner's in September get different `anyio`, different `starlette`. | [`backend/Dockerfile:34`](../backend/Dockerfile#L34) — `COPY requirements.txt ./` then install from it. That file is generated by `uv pip compile` and pins all 30 transitive packages exactly, not just the 11 I declared. |
| 3 | **Whether an LLM is reachable, and what it says.** My machine has a `GROQ_API_KEY` in `.env` and network egress. The runner has neither — and even if it did, the same input can produce different output. | [`.github/workflows/ci.yml:101`](../.github/workflows/ci.yml#L101) — `TRIAGE_PROVIDER: simulated`. CI runs the seeded deterministic fake: no network, no key, same answer every run. |

A fourth, found the hard way: **the node image is not on a fresh runner**. `kindest/node:v1.31.2` is
~1 GB, and on a slow link the pull dominates. Pinning the version at least makes the cache
meaningful.

## 2. Where this pipeline sits on the CI/CD maturity ladder, and what the next rung buys

**Current rung: continuous delivery — automated deployment to a production-like environment, with
the production deploy itself being a human decision.**

What is actually automated ([`cd.yml`](../.github/workflows/cd.yml)), on every push to `main`:

- the full suite re-runs on the merged result, not just on the branch;
- images are built and pushed to GHCR tagged with the commit SHA;
- an ephemeral kind cluster is created, the prod overlay applied at that SHA, rollout waited on, and
  the Ingress smoke-tested;
- images are signed with cosign and an SBOM is emitted.

Why not the rung above (**continuous deployment**): the cluster CD deploys to is created and
destroyed inside the job. There is no long-lived production environment that a merge updates. If one
existed, this pipeline would deploy to it unattended, which is what makes the gap a matter of
infrastructure rather than of pipeline design.

Why not the rung below (**continuous integration only**): PRs already build images and run a full
Compose integration, and merges publish and deploy. That is past integration.

**The next rung, and what it buys: GitOps.** Argo CD or Flux reconciling a long-lived cluster from
the repository, with `cd.yml` writing the new digest back to the overlay instead of applying it.

What that buys, concretely:

1. **The repository becomes the truth.** Right now a `kubectl rollout undo` (see
   [RUNBOOK §3a](RUNBOOK.md#3a-fast-and-imperative--the-3-am-answer-30-seconds)) leaves the cluster
   disagreeing with `main` and nothing records it. A reconciler would either revert my manual change
   or flag the drift.
2. **Deploy permissions disappear from CI.** Today the deploy job holds cluster credentials. Under
   GitOps the agent pulls; no external system needs write access to the cluster.
3. **Rollback becomes `git revert`** — one mechanism instead of the two in the runbook.

## 3. The exact line guaranteeing build-once-deploy-many, and what breaks without it

There are two halves, and both are needed.

**Deploy side —** [`k8s/overlays/prod/kustomization.yaml:19`](../k8s/overlays/prod/kustomization.yaml#L19):

```yaml
newTag: PLACEHOLDER_TAG      # replaced with ${{ github.sha }} by cd.yml
```

The image deployed is the one built from this commit, by immutable reference.

**Without it**, deploying `:latest` means the bytes running in production are whatever was pushed
last. Two consequences: "what is production running?" has no answer, and rollback is guesswork
because re-deploying the previous tag may fetch the same bad bytes. It is also an automatic −8.

**Build side —** [`frontend/src/api/config.ts:47`](../frontend/src/api/config.ts#L47):

```ts
apiBaseUrl: injected.apiBaseUrl ?? devBase ?? '',
```

The API base is read at **runtime** from `/config.js`, written by the container's entrypoint from
environment variables.

**Without it**, `import.meta.env.VITE_API_URL` would be inlined into the bundle by `vite build` — a
string literal in the JavaScript. The image would then only work in the environment it was built
for, and dev, staging and prod would each need a separate image built from identical source. The
image that was tested would not be the image deployed. See
[ADR 0002](adr/0002-frontend-runtime-config.md).

**Verified rather than asserted:** the same `civicpulse-frontend` image runs under Compose
(`BACKEND_URL=http://backend:8000`), under Kubernetes
(`http://backend.civicpulse.svc.cluster.local:8000`, [`k8s/base/frontend.yaml`](../k8s/base/frontend.yaml)),
and standalone with no backend at all. Only environment variables differ.

## 4. With a live LLM the service is probabilistic. What does "correct" mean, and how is CI deterministic?

### What "correct" means for a probabilistic component

Not "the category is right". That is a *quality* measure, it is a distribution rather than a
predicate, and no single input has a guaranteed output.

Correctness here is a set of **structural properties that hold for every input, whatever the model
says**:

1. **The output is in the domain.** `category` ∈ our enum, `priority` ∈ our enum, `summary` ≤ 140
   characters, `confidence` ∈ [0,1]. Enforced by `TriageResult` in
   [`backend/app/schemas.py`](../backend/app/schemas.py), not by trusting the model.
2. **A complaint is never lost.** `POST /api/complaints` returns 201 whatever the provider does —
   the invariant that `triage()` never raises.
3. **The provenance is recorded.** `triaged_by` says which reader decided, so a degraded run is
   visible rather than silent.
4. **Untrusted input cannot change the control flow.** An injection attempt cannot produce a
   category outside the enum, because the enum is enforced after the model replies.
5. **Latency is bounded.** 10-second hard cap, at most one retry.

Every one of those is a predicate that can be asserted on every run. *Quality* is measured
separately and reported in [`docs/TRIAGE.md`](TRIAGE.md) — it belongs in a report, not in a gate.

### How CI stays deterministic

By design, not by luck:

- **CI pins `TRIAGE_PROVIDER=simulated`** ([`ci.yml:101`](../.github/workflows/ci.yml#L101)) — seeded
  from a hash of the input, so the same complaint always classifies the same way, with no network.
- **Failure modes are injected, not waited for.** `AlwaysRaisingProvider` and `RawReplyProvider` in
  [`backend/tests/fakes.py`](../backend/tests/fakes.py) let the fallback and the validator be tested
  in milliseconds.
- **No `time.sleep()` in any test.** TTL expiry is tested by advancing a fake clock
  (`FakeClock.advance(31)`), so the 30-second cache TTL is asserted instantly and exactly.
- **Order independence.** The `clean_db` fixture truncates between tests; a suite that passes only in
  one order is not a suite.

Result: 91 backend tests, 84% coverage, green on every run.

## 5. HPA lag: how many seconds, where did the time go, what would reduce it?

**Measured** ([`docs/evidence/hpa-lag.md`](evidence/hpa-lag.md), raw capture in
[`hpa-watch.txt`](evidence/hpa-watch.txt)):

| | |
|---|---|
| Load began rising | t = 30 s |
| HPA changed the replica count | t = 70 s → **decision lag ≈ 40 s** |
| First new pod Ready | t = 73 s → **capacity lag ≈ 43 s** |
| Of which pod startup | **3 s** |
| Replicas | 2 → 8 |
| Peak CPU | 187% against a 60% target |

**Where the time went.** The striking part is that pod startup was only **3 of 43 seconds**. The
intuitive culprit — slow containers — was almost irrelevant. The rest was:

1. **Metrics staleness (~15–20 s).** metrics-server scrapes on an interval and reports a short
   rolling average. At t=30 s the reported utilisation still described a mostly-idle service. The
   capture shows it climbing through 13% → 26% → 59% → 126% in successive 15-second samples.
2. **HPA sync period (up to 15 s).** The controller re-evaluates every 15 s, so a decision can wait
   most of a period after the metric is available.
3. **Pod startup (3 s).** Small image, already on the node, fast uvicorn boot, readiness probe every
   5 s.

So the lag is dominated by **observation**, not by **action** — which inverts the intuition and is
the actual finding.

**What would reduce it:** a shorter metrics resolution and HPA sync period (at the cost of more API
traffic and more flapping); a lower target than 60% so scaling starts earlier; or a higher
`minReplicas` so the burst is absorbed without scaling at all.

**Why it matters:** for ~43 seconds the two original pods absorbed everything, hitting 187% of their
CPU request. Autoscaling did not prevent that overload; it ended it. `minReplicas` has to be large
enough to survive the spike alone — which is why autoscaling is not a substitute for capacity
planning.

## 6. Why VPA is in `Off` mode, and the failure mode of `Auto` alongside an HPA

[`k8s/overlays/prod/vpa.yaml:34`](../k8s/overlays/prod/vpa.yaml#L34) — `updateMode: "Off"`.

**The two controllers act on opposite sides of the same fraction.**

The HPA scales on CPU utilisation, defined as **usage ÷ request**. The VPA adjusts **the request**.
So in `Auto` mode:

1. VPA observes real usage and **raises** `requests.cpu`.
2. The denominator grows, so computed utilisation **falls** — without any change in real load.
3. The HPA sees utilisation below target and **scales in**.
4. Fewer pods carry the same traffic, so per-pod **usage rises**.
5. The VPA observes higher usage and **raises the request again**.

Neither converges. The replica count and the request size oscillate, and — because the VPA evicts
pods to resize them — the system is also churning pods while it does so. The PodDisruptionBudget can
slow that but cannot stop it.

There is a second, quieter problem: **the VPA's recommendation is polluted by the HPA's actions.**
Per-pod usage depends on how many pods there are, so the VPA is measuring a number the HPA controls.

**Recommender mode plus a human decision** is current industrial practice for exactly this reason,
and it is what this repository does. The loop is:

1. Record the requests guessed when the manifest was written — `cpu: 100m`, `memory: 192Mi`
   ([`k8s/base/backend.yaml:89`](../k8s/base/backend.yaml#L89)).
2. Run the load test.
3. `kubectl describe vpa backend-vpa` → commit Target, Lower Bound, Upper Bound.
4. Update the requests to match.
5. Re-run and report what changed about HPA behaviour.

> **Status:** steps 1–2 are done and the measured evidence is committed. Steps 3–5 require the VPA
> CRDs installed (`scripts/k8s-up.sh --vpa`); the recommendation is not yet committed. Stated plainly
> rather than fabricated — and what I would expect is that the 100m request is **too low** given the
> observed 187% peak, so the Target lands nearer 200m, after which the same load produces a lower
> computed utilisation and the HPA scales to fewer replicas for the same work.

One thing the HPA/VPA conflict does **not** apply to: memory. The HPA here scales on CPU only, so a
VPA memory recommendation has no feedback path into it.

## 7. `internal: true` blocks outbound traffic. Where does that leave a service calling a hosted LLM?

[`compose.yaml:232`](../compose.yaml#L232) — `internal: true` on the `internal` network. Docker omits
the gateway, so containers on it have no route off the host. Verified: from `database`,
`wget https://example.com` fails.

**The tension:** the backend must reach `api.groq.com`, but it must also reach a database that has
no internet route.

**How it is resolved here:** the backend is the **only service on both networks**
([`compose.yaml`](../compose.yaml), `backend.networks: [edge, internal]`). `edge` is a normal bridge
with a gateway, so outbound HTTPS works; `internal` reaches Postgres and Redis. The frontend joins
`edge` only, the database and cache join `internal` only.

That makes the backend the deliberate, single, reviewable place where edge traffic can reach data —
and the same property the design is for is directly demonstrable:

```sh
docker compose exec frontend ping database   # "bad address" — cannot even resolve
```

**What it costs, stated honestly.** The component with internet egress is also the component holding
the database credentials. Network segmentation has not removed that risk, it has *concentrated* it
into one service, which is a trade rather than a win. What it buys is that the internet-facing
component — nginx serving a SPA, the likeliest thing to be compromised — has no path to the data at
all.

**Other defensible designs**, considered and rejected:

- **An egress proxy on `edge`,** with the backend on `internal` only. Strictly better isolation: the
  backend never has direct internet access and the proxy allow-lists `api.groq.com`. Rejected as a
  sixth container for no marks, but it is what I would build for real.
- **`OllamaTriage` on `internal`.** Removes the question entirely — no egress needed, no PII leaving
  the machine ([ADR 0004](adr/0004-pii-and-data-governance.md)). This is a supported path: the model
  weights are pulled once by a separate `ollama-pull` service that sits on `edge`
  ([`compose.yaml:215`](../compose.yaml#L215)), after which Ollama itself needs no network.
- **Triage asynchronously from a worker on `edge`.** Right at scale; more moving parts than this
  assignment justifies.

## 8. The failure: something that cost more than an hour

### Symptoms

`alembic upgrade head` failed on a clean database:

```
sqlalchemy.exc.ProgrammingError: (psycopg.errors.DuplicateObject)
type "category" already exists
[SQL: CREATE TYPE category AS ENUM ('water', 'electricity', ...)]
```

Worse, it was **not reproducible from a clean slate**: the first run left the enum types behind but
no `alembic_version` row, so the second run tried to create them again and the error looked
intermittent.

### What I wrongly believed first

That the test database was dirty — that a previous run had left types behind and the fix was to drop
the container and start again. I did that twice. It worked once (misleading me further, because the
very first run on a truly empty database succeeds) and failed again the next time.

My second wrong belief was that `downgrade()` was broken, since `downgrade(base)` had clearly not
removed the types. I spent time reading the downgrade path, which was fine.

### The line that told me the truth

Running the migration with echo on, and reading the SQL in order:

```
CREATE TYPE category AS ENUM (...)       <- my explicit .create(bind, checkfirst=True)
CREATE TABLE complaints (...)
CREATE TYPE category AS ENUM (...)       <- emitted AGAIN, by create_table()
```

**The type was being created twice in the same migration.** SQLAlchemy's `create_table()`
automatically emits `CREATE TYPE` for any enum column, in addition to the explicit `.create()` call I
had already made. `checkfirst=True` on my call did nothing, because my call was the one that
succeeded — the *second*, implicit one failed.

### The fix

Create the types explicitly, then declare the columns with `create_type=False` so `create_table()`
does not re-emit them —
[`backend/alembic/versions/0001_initial_schema.py`](../backend/alembic/versions/0001_initial_schema.py):

```python
postgresql.ENUM(*values, name=name).create(bind, checkfirst=True)
category = postgresql.ENUM(*CATEGORY, name="category", create_type=False)
```

### What I took from it

Two things.

**The failure was not intermittent; my mental model of "clean" was wrong.** A database with orphaned
types and no `alembic_version` row is a state I had not considered, and it is exactly the state a
half-failed migration leaves. The `conftest.py` fixture now runs `downgrade(base)` before
`upgrade(head)` on every session, so every test run starts from a state the migration itself
produced.

**"Idempotent" is a property of the whole operation, not of each step.** `checkfirst=True` made *my*
statement idempotent and I assumed that was enough, without asking what else emitted DDL.

A second failure worth recording, because it cost nearly as long and is specific to how this code was
written: **fabricated identifiers**. The image digests and an `apt` version pin
(`curl=7.88.1-10+deb12u12`) were plausible-looking and did not exist, and the builds failed with
errors that read like network problems. Real digests came from `docker buildx imagetools inspect`;
the curl dependency was removed in favour of the Python already in the image. See
[`docs/AI-USAGE.md`](AI-USAGE.md).

## Appendix: the two indexes, and the query each serves

[`backend/app/models.py:86-88`](../backend/app/models.py#L86-L88). An unexplained index is cargo cult,
so:

**`ix_complaints_status_priority` on `(status, priority)`** serves the dashboard's default view —
`ComplaintRepository.list_page()` in
[`backend/app/repositories/complaints.py`](../backend/app/repositories/complaints.py):

```sql
SELECT * FROM complaints WHERE status = 'open' AND priority = 'high' ...
```

Column order matters: `status` is filtered on almost every dashboard request and `priority` only
sometimes, and a composite index can serve a prefix of its columns but not a suffix. `(status,
priority)` serves both `WHERE status = ?` and `WHERE status = ? AND priority = ?`; the reverse order
would serve neither well.

**`ix_complaints_created_at`** serves the `ORDER BY created_at DESC` on that same paginated query,
and the time-ordered read behind `/api/stats`. Without it, every page of the dashboard sorts the
whole table.

Honest caveat: at 37 rows the planner will sequential-scan regardless, because a scan of one page is
cheaper than an index lookup. These indexes are sized for the four-hundred-item Monday queue in the
problem statement, not for the seed dataset.
